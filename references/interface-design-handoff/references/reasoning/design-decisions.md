- **DL-95 · TRENDS CARRIES TWO KINDS OF DEPTH. THE GRID CARRIES COMPARATIVE DEPTH, THE ENLARGE VIEW CARRIES SINGLE-SERIES DEPTH, AND THE ENLARGE VIEW IS THE DECLARED HOME FOR EVERY FUTURE DEPTH FEATURE** — 2026-09-18 · **Accepted** (Keith, "keep the grid version of the chart glanceable and make the full screen one have the capability to go in depth").

  **The model.** The grid is read at a glance and supports light interaction, hovering a point to read its value. The enlarge view is where one chart gets control the grid cannot give it. This is overview then zoom then details-on-demand, which DL-64 already named as the governing model for this surface and noted was "already correct here via the enlarge modal". ⭐ **So the grid and the enlarge view are ONE decision rather than two**, and the grid is not a compromise on DL-64, it is the half of that model DL-64 could not have while every chart was full width.

  ⛔ **THE WORD "GLANCEABLE" IS REJECTED FOR THE GRID, AND THIS IS THE LOAD-BEARING PART OF THE ENTRY.** `area2-spec.md` heads this tab **Tab 2 Trends (analysis depth)** and its decision 4 splits **Overview as glance and today** against **Trends as history**. Describing the Trends grid as glanceable puts Trends into Overview's role and pushes the depth the spec asked for one click further away than the spec put it. **The accurate words are comparative depth for the grid and single-series depth for the enlarge view.** Reading one moment in time across seven charts on a shared domain is a depth Overview can never offer, because Overview shows today. ⭐ **Framed that way the two-tier model is not a retreat from the analysis-depth label, it is the first version of this tab that honours it**, since nine full-width charts in one column cannot be co-visible and therefore cannot be compared at all. **Anyone challenging this decision will be holding the spec, so the language has to survive that.**

  ⚠️ **The two goals fight in exactly one place, and it decides the column count.** Small cells serve everything-visible-without-scrolling. Hover-to-read needs a cell wide enough that a bar can be hit and an axis can be labelled. **So the number of grid columns is set by the smallest cell in which hover-to-read still works, which is a measurement rather than a taste call**, and it is Code's to run on real data. It also licenses the grid to be sparse, since depth is one click away and a cell does not have to carry everything.

  ⛔ **A PER-CHART DATE RANGE IN THE ENLARGE VIEW IS REJECTED. WHAT IS APPROVED IS A ZOOM INSIDE THE CURRENT RANGE.** Keith raised a modal-local range that deliberately does not affect the background. Rejected on three grounds. It puts two time windows on screen in one session and the user cannot tell which they are reading. On close it either discards, which makes it pointless, or it persists, which leaves the grid behind it showing a comparison that is quietly false for one chart. And it adds a second writer beside a URL param `AB#945` was explicitly built to keep single-writer. ✅ **The approved shape is drag to narrow and double-click to reset, always a subset of the window the tab is on, computed client-side over data already fetched.** Same depth, one source of truth, and the grid can never lie.

  ⛔ **AND MOST OF THE DEPTH FEATURE SET IS BLOCKED ON A BACKEND PARAMETER THAT DOES NOT EXIST.** Granularity as a request parameter has been an open DD row since 2026-08-19, **thirty days silent as of 2026-09-18**, and it was confirmed on 09-07 that `app/api` carries no bucket or interval parameter anywhere. A per-chart range could only re-request from and to and accept whatever bucket width the server chose. **So the shell gets built and the features do not get designed against a capability the API lacks.** This is also the strongest argument for the zoom being client-side.

  **What DL-64 actually rested on, quoted because the amendment turns on one sentence.** Its grid rejection was that two charts side by side *"render different ranges at different pixel widths, so reading a vertical time slice down the page tells you nothing."* Two conditions, different ranges and different widths.

  ⛔ **`AB#1004` REMOVED THE FIRST CONDITION AND THAT IS WHY THE REJECTION NO LONGER HOLDS AS WRITTEN.** The Trends route loader now computes one numeric domain from the URL window and maps five differently named time keys onto a common key, so **every time chart renders the identical range by construction** and no series can widen it.   ✅ **What SURVIVES, and it is the whole remaining cost.** DL-64's other half, that a shared axis *"lines up and is drawn once"*, cannot hold for every chart in a grid, because one axis at the foot of a single column has nothing to sit under when charts are side by side. **The trade is therefore no longer comparison against density.
